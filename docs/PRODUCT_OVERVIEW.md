## 从一条消息开始，把协作连起来

TinyIMX 将日常协作放进清晰的原生界面：找到联系人，继续私聊或群聊，查看历史与未读，分享经过校验的文件，再按需请本地 AI 帮助理解当前会话。界面中的消息、成员、文件任务和模型响应连接真实后端服务。

![TinyIMX 原生客户端：会话列表、群消息、授权附件](../clients/qt6/preview-features/messages.png)

|实时沟通|有序协作|可信共享|
|---|---|---|
|私聊、群聊、历史、未读和离线恢复，在同一工作区连续完成。|当前成员、角色、禁言和历史访问各有明确权限边界。|独立文件通道、SHA-256 完整性校验和接收者授权，让附件与消息自然衔接。|

## 50K 在线用户下的真实业务能力

8 vCPU、16 GiB Ubuntu 同机运行完整服务，Windows 原生客户端维持 50,000 个认证在线连接。两个工作点各持续 300 秒，每个账号都参与收发；消息保存、接收确认、未读投影与独立存储核验全部完成。

| 业务工作点 | 1,000 条/秒 | 1,250 条/秒 |
| --- | ---: | ---: |
| 完整成功 | 300,000 / 300,000 | 375,000 / 375,000 |
| 持久化 ACK 平均 | 9.258 ms | 13.290 ms |
| 持久化 ACK P99 | 48.573 ms | 60.553 ms |
| 128 B 正文吞吐 | 128 KB/s · 1.024 Mbit/s | 160 KB/s · 1.280 Mbit/s |
| 收尾待发布与待确认 | 0 / 0 | 0 / 0 |

每条消息的可靠链路与业务权限一起保留，性能数字和真实持久状态相互核对。测试采用原生私聊同步 WAL 与 RocketMQ LOCAL 同步刷盘；两个 Gateway 均衡承载，本组私聊对位于同一 Gateway。[查看完整报告与精确 QPS 计算](performance/FINAL_CAPACITY_20261027.md)。

## 消息的每一步，都有明确状态

从客户端提交到服务端持久化、目标端接收，再到已读状态，TinyIMX 将这些阶段分开处理。CID 幂等应对重复提交，MID 与接收确认处理重复投递，离线消息支持重连恢复。原生私聊存储配置将消息、索引、未读真值和待发布事件放入同一同步提交，后台发布进度也有恢复路径。

网络模块基于 epoll / Reactor，实现连接管理、跨线程任务投递和发送缓冲控制；双 Gateway 通过路由与 SessionEpoch 处理重新登录和旧连接失效。有界任务执行和截止时间控制让过载能够被识别，服务停止时对已接纳任务进行收尾。

## 群组协作，权限落实到每次操作

群成员、角色、禁言、邀请、转让和解散由服务端校验；历史访问同时考虑当前成员身份与消息快照授权。客户端展示操作入口，最终权限由后端决定。

![TinyIMX 群成员与角色管理](../clients/qt6/preview-features/groups.png)

## 文件任务与聊天各自流畅

文件字节通过独立通道传输，聊天消息承载授权附件卡片。上传采用分块校验和整体终验，上传 ID 状态机处理取消与完成竞态；HMAC 授权绑定接收者。任务界面集中展示进度、重试与恢复状态。

![TinyIMX 文件上传与下载任务](../clients/qt6/preview-features/files.png)

## 本地 AI，按需接入上下文

客户端连接 Ollama，提供流式问答、模型检测和停止生成。用户决定是否附加当前已加载会话片段；模型响应失败不阻断聊天。后端另提供 C++ MCP 服务，8 个只读工具经服务端派生身份和 gRPC 权限校验，读取已授权的资料、好友、会话、历史、群成员与文件元数据。

![TinyIMX 本地 AI 流式问答](../clients/qt6/preview-features/ai.png)

桌面 Ollama 问答与后端 MCP 是两条可独立使用的扩展链路。MCP 的价值是复用既有业务权限读取上下文；工具数量不直接代表模型回答速度或准确率。
