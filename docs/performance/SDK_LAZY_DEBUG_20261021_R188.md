# SDK 调试文本的延迟格式化候选（PERF-187—213）

2026-10-21。状态：固定源码补丁、日志契约、完整隔离 SDK 构建、九个服务的动态依赖加载及四组真实 MQ 功能验证通过。完整负载性能对照尚未执行。原来安装和运行的 SDK 未替换，默认开关未推广。

## 原因与实现

R166 的当前组件调用栈出现 `ReceiveMessageStreamReader::OnReadDone → DebugString → TextFormat`。R179 对实际安装库的反汇编核验确认，成功读取回调会先构造响应文本，再读取日志级别；不是仅根据源码推测。安装库 SHA-256 为 `d3657532a5eca81da38e09807bfe4014e769253ff03b135829d8a9b0037555bf`。精确 CPU 占比尚未测出，不能据采样叶节点比例推算整机收益。

补丁限定于固定 Apache RocketMQ C++ 源码的两个文件、12 个调试文本表达式：

- `ReceiveMessageStreamReader.cpp` 中 1 处响应 `DebugString()`。
- `ClientManagerImpl.cpp` 中 11 处发送、接收、ACK、心跳等请求/响应文本。

新增 `LazyLogValue`，将文本生成交给 fmt 实际格式化时执行。使用 `TINYIMX_ROCKETMQ_LAZY_DEBUG_ENABLE=1` 启用；默认 0 仍在构造参数时求值。未设置或非法值均关闭。它不是简单在调用前检查 `should_log`：运行级别关闭 DEBUG、但启用 backtrace 时，spdlog 仍能格式化并保存该条调试记录。

补丁保持 C++11，helper 在原 `spdlog/spdlog.h` 之后包含，保留原源文件的 fmt 包含顺序。SDK 同时带有 spdlog 的 bundled fmt 8.1.1 和独立 fmt 9.0.0，两种顺序分别验证。WARN/ERROR 的文本、请求内容、回执映射、超时、重试和持久化代码均不属于此补丁的修改集合。

实现位于 `patches/rocketmq-cpp-5.1.1/LazyLogValue.h`，可复现应用工具为 `scripts/apply_rocketmq_lazy_debug_patch.py`。工具先验证两文件的固定前像哈希和 1/11 个表达式数量，再写入；拒绝陌生改动、陌生 helper、符号链接和不匹配的中间文件。匹配的部分应用可恢复，重复运行不重复包裹表达式。它只修改显式指定的 SDK 源码副本，不安装或覆盖运行库。

## 真实 MQ 已执行，完整性能仍待验证

`run_sdk_real_mq_r192.py` 的 r3 已用四个全新、严格限定的 topic/group，以同一候选库 OFF/ON/ON/OFF 分别完成 32 条正文、消息键、无效回执拒绝、一次漏确认后的真实重投、逐条结果和停止后失败，共 128 条。程序核验实际加载库的公共符号来源，拒绝误用原 SDK。每组最大收取批次均为 16，四组全部通过，原 2,292 个容器及保护数据库、binlog 的后置检查通过。

R199 在执行前审查中修正了验证程序的漏检：首次接收也必须校验已发布消息键；DEBUG 空接收必须成功，不能把失败但无消息当作通过。移除未受控制器支持的部分续跑入口；SSH 超时或本机进程创建失败时仍提取现有证据，若成功运行但提取不全也判失败。部分实验不会自动重发或重置 offset。这些修正已随 r3 编译并执行，原 R199 的 AST-only 结果仍作为历史记录保留。

两次失败没有删除或重写。r1 的 C++ 编译、链接和 Java 编译通过，但控制器错误假设代理已公开映射 8081，故在创建命名空间前失败；r2 改为读取 Docker backend 的真实 IP/别名并验证 TCP 可达，随后测试客户端因配置拒绝退出，尚未启动发布。原因是复制了 `unread_projection.enable=true` 却没有启用其 MySQL/Redis 依赖。r3 的公开 dry-config 模式实际复现了同一拒绝消息，并在每组创建命名空间前验证新配置。

r3 只启动 producer 和 SimpleConsumer，显式关闭投影器组件并保留原消费选项；没有启动 SQL/Redis 投影链，也没有修改产品配置校验。r2 已创建的空命名空间保留，r3 使用 `codex_perf192_events_20261021_r3_(off1|on1|on2|off2)` 及对应独立 group。客户端通过 Linux guest 到现有 Docker backend 验证功能，没有更改代理映射或容器配置，**不属于 Windows 原生发压拓扑的性能对照**。每组约 18 秒包含规定的不可见窗口及空收取等待，不能拿其差值解释吞吐或延迟收益。

SDK 日志探针沿用进程既有 HOME，不修改系统变量，不复制其他进程的日志。先固定文件 sink 的 DEBUG 阈值，以 INFO 完成消息检查，再用一次 DEBUG 空接收检查两个修改源文件的真实格式化路径。通过本次 cohort/PID 标识提取私有日志证据；已有日志的 inode 和原字节前缀必须保持，临近轮转时拒绝启动。

R200 再核对候选实际 ELF，而不只检查补丁文本：旧库回调的 `DebugString` 调用位于 `0x22859f`，级别读取位于其后 `0x2285a4`；候选在 `0x22d3c6` 按延迟开关分支，关闭时转到 `0x22ddd0`，在 `0x22dde8` 执行原先的提前文本生成；开启时可以先进入 `0x22d40d` 的级别读取。完整反汇编及两个库哈希保存在 `PERF200-sdk-actual-elf-audit-r1/`。这是静态机制证据，不表示已运行新库，也没有给出 CPU 占比或延迟收益。
