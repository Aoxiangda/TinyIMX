# 实际 Proxy→Broker ACK 批量与失败范围（R234—R238）

2026-10-21。默认配置未推广。已完成同镜像独立 Proxy 的两组四轮功能实验，共 256 条消息；实际抓包确认后端请求减少，同时确认损坏回执会扩大整批失败范围。没有新的完整 IM CPU、P99、QPS 或容量成绩。

## 实验边界

- 原 Ubuntu 仍为 8 vCPU / 16 GiB；此处使用独立临时 Proxy，配置 heap512MiB、容器1GiB、CPU2，作为有界功能仪器。它不等同于正式对标配置，运行时间和资源不能与原 Proxy/WuKongIM 当作性能对照。
- 使用原运行 Proxy 镜像 `sha256:7e8f6c9dbd9df742ed26ba69c00d4ad69e2f86a56f3ca7782ff8144dd0798132`。原 Proxy、其配置及原业务程序保持运行；临时实例没有宿主公开端口，没有继承业务可写挂载。
- 固定 SDK `6f9b0a661651bb7120209c2842005b50c8daa24cd2dca3cae6450b61208a90f4`，固定 R224 transport archive；八组均使用客户端批量 ON、日志优化 OFF，只在临时 Proxy 切换 `enableBatchAck`。
- 每组新建独立 topic/group，仅从原模板复制配置并改名，不重置或删除原消费位置。每组先发布32条，逐项验证消息 ID、topic、tag、key及正文。
- 抓包容器仅加入该临时 Proxy 的网络命名空间，过滤它发往 Broker10911 的 TCP；从 Proxy 放行启动前就开始，排除原业务 Proxy 流量。截获文件上限4MiB，结束时 kernel drop 为0。
- 临时容器按本次创建的精确 ID、名称和 owner 标签核对后结束/回收。原2292容器、20个健康服务、保护SQL行数和binlog不变。

## R235：客户端批量之后，后端仍可能逐条

| 临时服务端开关 | 两次各完成消息 | SDK批量提交 | 实际单条Broker ACK | 实际批量Broker ACK |
|---|---:|---:|---:|---:|
| OFF1 / OFF2 | 32 / 32 | 3 / 3 | 32 / 32 | 0 / 0 |
| ON1 / ON2 | 32 / 32 | 3 / 3 | 0 / 0 | 3 / 3 |

两组OFF和两组ON均通过漏确认后真实重投，以及超过10秒不可见期后已确认数据不再出现的检查。每组中最初刻意清空一条native handle，SDK不提交该无效项，真实重投后才确认，所以最终有效提交条目仍为32。

这把 R229 的源码/启动值推断推进为同一官方镜像下的真实协议对照：客户端3次批量请求，并不自动消除 Proxy 内部32次单条处理；独立服务端开关开启后，捕获到的 Broker ACK 请求变为3次。正常测试这一特定批次形成方式下，请求数减少90.625%。这不是CPU减少90.625%，也不是正式业务一定形成同样批次。

原运行 Proxy 的启动值仍为 false；本次没有改它。服务端类分支与请求码来自安装镜像本身，`ACK_MESSAGE=200051`、`BATCH_ACK_MESSAGE=200151`。

## R236：真实损坏回执扩大失败范围

在第一批16条中，将第一条收到的原生回执替换为非空、格式损坏的字符串；其他消息的ID和回执保持原样。不是本地null handle，而是真实请求到达 Proxy 后失败。

| 临时服务端开关 | 第一批失败数 | SDK累计提交条目 | 最终确认消息 | 抓到的Broker ACK |
|---|---:|---:|---:|---|
| OFF1 / OFF2 | 1 / 1 | 33 / 33 | 32 / 32 | 两组均32次单条 |
| ON1 / ON2 | 16 / 16 | 48 / 48 | 32 / 32 | 分别3次/2次批量 |

ON1的SDK总调用为4次，ON2为3次；重投返回批次不同，不能挑选一个当成固定合并率。两者第一批都明确返回16项失败，未误报成功；随后全部恢复。其Broker批量请求数等于SDK提交数减1，因为第一批在解析损坏回执时失败，没有发往Broker。

对应固定源码：`AckMessageActivity::ackMessageOneByOne` 分别处理entry并收集状态；`ackMessageInBatch` 先解析全部receipt，再调用批量接口。后者遇到坏格式会在批量调用之前异常退出。该实验验证了这一失败范围差异。

本测试只证明 Main transport 的逐条失败传递和MQ重投恢复；没有执行真实 Redis projector，不声称已经证明整批重投下业务投影只生效一次。损坏项在首位，位于中间时回执缓存已有部分操作的恢复仍需单独验证。缺少这些证据时，不开启原配置。

## R237：字节分析及额外发送的核对

对八份原始pcap重新解析，所有原请求计数与原解析器一致，TCP重传字节均为0。Ethernet/IPv4/TCP序列重组拒绝截断、缺段、冲突重传、非本次源地址及外来group；9项夹具覆盖分段、乱序、重传与拒绝路径。ACK计数按完整Remoting帧，不以TCP包数或SDK函数名代替。

正常轮ACK Remoting帧实际总字节，OFF两组均10351，ON两组均1863。它只含长度字段、JSON头和body，排除了前端gRPC、TCP/IP头、连接/控制流量和重传；也不代表磁盘写入量。

另一个比较细节已显式保留：`off1/off2`命名4字符、`on1/on2`3字符。按实际ACK帧内group/topic文字出现次数将标签宽度调整到4字符，得到OFF10351、ON1881字节的分析估计。此调整不是新抓包，不把原始82.00%字节差当成严格等长命名实验，更不把它当CPU或P99收益；正式用例应直接采用等长数据域名称。

抓包曾显示每组有36次发送请求，而测试只发布32条。已继续拆分：32次分别是本次独立topic的32个精确正文，另外4次属于 `DefaultHeartBeatSyncerTopic`。实际安装 `ProxyConfig` 字节码的 `heartbeatSyncerTopicName` 默认值与之对应；这4次系统发送不计入业务消息，不作为业务重复发布。结果见 `PERF237-proxy-ack-wire-analysis-r2/result.json`。
