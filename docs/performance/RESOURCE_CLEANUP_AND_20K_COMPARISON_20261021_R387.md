## 仍需继续追查的性能差异

本轮是一个按相同提供负载执行的先后顺序对照，不是重复 ABBA、最大容量、长稳态或高可用结论。协议/加密、容器与原生进程形态、接收端 ACK 与持久化约定也存在差异，倍数不能直接解释为某一个模块的算法效率。

R388 对两个已完成正式窗口做只读后分析：TinyIMX 的 Windows 系统页输入平均 2284.35 页/s，Peer 5.96 页/s。相应 VMware 总 PageFaultCount 增量分别为 297126 / 15998；客户端增量为 17528 / 38709。不同采样跨度及全部原始值已保留。这些计数不能确定硬错误来自哪个映射/文件，也不能折算成网关或 Reactor 的延迟：系统 Pages Input 包括文件映射硬错误和页面文件读取，PSAPI PageFaultCount 同时含软、硬错误；VMware 工作集也不等同 guest 已用内存。

后续需要独立的同负载诊断点，取得进程级硬错误/文件来源，并与网关、RPC、存储及后台工作阶段耗时对照；随后再跑关闭诊断的重复配对及单变量优化。R355 保存的当前候选 CID 规范化和用户存在性 SQL 桥接差异仍有效。本轮没有用资源差异替代服务端源码定位。

本次多次重启也使 R360/R362 的旧 Proxy StartedAt 证明过期。R395 已完成本次启动的只读复核：StartedAt 为 `2026-10-21T11:09:10.769199475Z`，相同镜像、JAR 和配置 SHA，最新启动日志仍为 `enableBatchAck=false`，没有配置覆盖，也没有修改设置。后续 SDK 六臂对照还需把这份证明纳入新代次配置后再执行；旧结果及保护断言保留。R395 不是逐个 RPC 的服务端方法追踪。
