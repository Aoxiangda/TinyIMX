## 已确认的问题与尚待证明的归因

1. **50k登录处于CPU争用区间。** 20秒局部爬坡采样中8核约94.7%忙碌，认证30661→32592，约96.6用户/s；UserService约1.59核，MySQL约0.78、两Gateway各约0.72、Redis约0.69、nginx约0.51、MessageService约0.48、worker约0.46。只覆盖局部爬坡，不能当稳态分布或完整火焰图。源码密码校验PBKDF2-SHA256迭代100000；采样尚未证明这些CPU都花在密码函数。不能降低密码成本、跳过鉴权或扩大截止时间来制造PASS。
2. **ACK前有串行服务调用。** 源码私聊先权限RPC、路由、持久化RPC、稳定消息ID幂等未读投影，再完成相应投递/ACK。投影涉及正确性和ACK返回字段，不能直接移到ACK后或省略。30k慢请求样本Gateway持久化平均75.21ms（522条），内部持久化平均23.96ms（488条）；权限18.29ms、未读23.00ms，派发最大227.55ms。独立慢样本均值不能相减归因或相加当整体P99；57条同消息配对的RPC减repository平均18.92ms，仍混合服务排队/网络/调度/编码成本。
3. **数据库COMMIT与连接池曾有明显成本。** 30k内部样本COMMIT平均11.10ms、最大111.92ms；pool8→16对照消除了本轮部分3秒失败，但尚未解决规模尾延迟。40个行锁快照当前等待0，不能证明全程无行锁；SUM_LOCK_TIME也不是行锁指标。继续保持flush1/sync1/doublewrite和原隔离级别。
4. **全局待投递账号发现是可测后台成本。** 完整10k/30k/失败50k运行SQL摘要均值约81.34/101.44/107.91ms。当前计划使用原覆盖索引与loose group-by，不是已证实全表扫描；rows_examined=0属于引擎计账，不能解释成无工作。旧012两索引联合候选曾回退，不能重复接受。013只验证(status,to)一个索引，保留全部原索引与历史Pending。需要查询一致性、优化器选择及真实业务A/B证据；DDL多一项也增加写入/接收确认维护成本，可能回退。
5. **心跳、在线状态维护及同机客户端会竞争CPU。** 10k/30k每15秒全体心跳（5秒为资源采样），大量非业务流量仍走事件循环、Redis更新、网络和客户端；100私聊/s不能代表所有在线用户都在持续发业务。需要在同在线规模比较业务速率曲线，并用同消息ID关联客户端、Gateway、服务和SQL计时，避免用不相同样本分位数拼接。
6. **功能正确性还有独立缺口。** Ollama实际位于guest127.0.0.1:11434，仅有qwen2.5:7b；原AI配置host.docker.internal/qwen3:8b不匹配。隔离MCP page50八业务工具和两个鉴权/schema负例实测PASS，原19实例/配置不变；page100会话实测HTTP200/isError=true/invalid_argument，原因工具schema允许100而MessageRpcClient上限50，尚待代码修复。正式principal1不存在、模型推理与AI性能均尚未通过。隔离测试群26、文件16和全部失败保留，不重复制造夹具。
