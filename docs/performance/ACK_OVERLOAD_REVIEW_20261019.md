# 持续过载、接收确认重投放大与候选隔离方案

这份记录固定本轮已执行事实及下一项实验。性能目标尚未达到。原始失败保留，候选默认关闭，不能用源码实现或单元测试替代端到端性能验收。

## 3. PERF-057：确认被共享任务预算拒绝

源码 `HandleReceiverChatDeliveryAck` 通过 `SubmitSessionBusinessTask(MessageExecutor(), ...)` 提交；私聊发送、跨网关转发也使用同一消息执行器。`kMustRun` 只保证已被接受任务的执行责任，不能保证被拒绝的 ACK 入队。拒绝分支记录告警后返回。

实际日志中，37350 个正消息范围共 22744 次接收 ACK 入队拒绝。414 条最终 pending 的 MID **全部**对应至少一次 `receiver ack business task rejected, status=overloaded`，未关联 durable-uncertain、mutation-before-failure、unknown-attempt、unknown-message 或 receiver-mismatch 告警。客户端另有 22387 次协议重复投递。这支持“确认被拒 → 继续重投 → 更多转发/确认任务争用共享预算”的放大路径，但不能据此断言每一次排队都仅由这一因素引起。

414 条内容仍存在 SQL，不能描述成内容丢失。也不能把客户端接收 ACK 写入 socket 当成数据库已确认。该时点尚未重放或修补，原始 414 条失败快照保留；后续正常重连的恢复结果见第 7 节。初版后处理错误地预设成功子集全正确而断言退出，之后核对同一子集 SHA 并重新只读核验，414 条错误仍存在；失败没有改判。

WuKongIM 普通接收回执处理主要推进内存重试状态；TinyIMX 还要求推进 MySQL 接收状态。因此可以借鉴事件路径隔离，不能直接删除确认事务或替换成仅内存回执。

## 4. 默认关闭的 PERF-057 候选

`TINYIMX_RECEIVER_ACK_WORKER_THREADS` 不设置时保持共享执行器。显式设置 4、8 或 16 后，私聊接收 ACK 使用单独的有界执行器；其他消息路径保持原执行器。

- 原消息 pending 总预算按 3:1 划分。当前 512 变为发送/转发 384、ACK 128，合计仍为 512，不扩大总队列。
- 原消息工作线程保留；ACK 增加独立线程，额外并发和资源成本必须计入比较，不当成免费收益。
- ACK 继续按 MID 排序，保留 SessionEpoch、登录用户、接收者、投递序号、仓储权限与 COMMIT 边界；组聊路径不受本候选影响。
- ACK 队列本身仍会有界拒绝，没有无限缓冲或无限重试。停机先完成消息执行器，再排空 ACK 执行器，依赖对象在排空前保活。
- 新增饱和、错误接收者、ACK 自身过载、MustRun 取消及 drain 回归；还必须通过真实网络与数据库压力验证。

架构改动局限于 Gateway 内任务隔离；消息协议、五服务职责、MySQL/Outbox/MQ 流程均未替换。**候选构建、回归通过也不等于应保留，必须依据 OFF/ON 实测。**
