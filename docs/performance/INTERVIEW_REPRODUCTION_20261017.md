## 先测什么、如何定义上限

8 核 / 16 GiB 不对应一个固定的消息 QPS。“网络字节回显”“带认证的连接承载”“服务端入队 ACK”“持久化 ACK”“接收端收到并确认”需要各自计数。固定配置下，应给出满足延迟和正确性要求的最大持续负载，以及不满足要求时的失效位置。

| 层次 | 工作负载 | 必须保留的结果 | 当前状态 |
| --- | --- | --- | --- |
| 环境 | CPU、空闲换页、4 KiB 写入 + fsync | 逐秒 CPU / PSI / 内存 / 换页；虚拟磁盘确认延迟 | 已完成首轮 |
| 传输 | 相同字节回显，无认证、DB、JSON 业务 | 报文大小、连接数、提供/完成速率、计划/实发延迟、错误、两端资源 | 首轮及失败诊断已完成，环境校准继续 |
| IM 业务 | 认证长连接、在线私聊、接收确认、持久化与离线恢复 | 完整请求分母、负 ACK / 超时、持久化与投递延迟、丢失/重复、积压 | 10k 私聊真实基线已执行；正常 6000 条全量 SQL 核对通过但 P99 不合格；混合负载原版出现超时，候选 ABBA 进行中 |
| 稳定性 | 候选容量下混合负载 | 至少 5 分钟容量复核，再做 30 分钟稳定性验证 | 待执行 |

容量搜索采用阶梯增加提供速率，出现超时、负 ACK、持续积压或明显客户端受限后停止上探，定位后再细化边界；不是持续加压直到 OOM。每个有效比较点交替重复，避免只选择较好一轮。记录客户端 CPU、发送迟到、未发请求与实际完成速率，不能只统计成功请求 P99。

工程验收目标将在传输基线及同语义业务对照完成后设定。第一步应复现原有 100 msg/s + 20 页/s 条件；随后寻找在同样可靠性语义下仍满足持久化 ACK P99 ≤ 100 ms、页面 P99 ≤ 100 ms 的持续容量。100 ms 是本次拟采用的工程目标，不是行业统一标准。1000 msg/s 等更高目标必须经过实测才能承诺。

## 复盘与优化边界

目前新增基线工具、可选回显适配目标，并在独立工作树修改一处 Outbox 过期清理 SQL 候选。真实 A/B 只临时替换 Relay，使用自动恢复控制器保留原容器身份及镜像；未改变架构、消息协议、事务边界、MQ、ACK、权限或登录行为。回显适配器复用冻结快照的网络源码，原 Gateway 没有被替换。

业务优化将逐个问题记录：调用路径 → 证据 → 修改 → 正确性回归 → 同条件 A/B → 架构/语义影响。先排除发压端和测量热路径开销，再决定是否调整 RPC、SQL、Redis 或队列。未有证据前不把 epoll 改为 ET、不放宽持久化、不移走 ACK 所承诺的操作，也不通过改配置追求简历数字。

负载生成需同时记录计划发送与实际发送两条时间轴，以避免低估积压延迟。这个测量原则可参照 [wrk2 的延迟说明](https://github.com/giltene/wrk2)；本次 TCP 工具不把 HTTP wrk2 直接用于 TinyIMX 协议。

## 完整IM对标语义准备

固定WuKongIM提交 `a888f89533d0e7d1b2030e06504ca97f1ad891d4` 的发送处理为permission→persist→sendack。存储Batch.CommitWait最终等待 `bt.Commit(pebble.Sync)`；因此正常持久化开启时，可进一步验证其同步提交ACK及恢复语义。相关源码：[发送路径](https://github.com/WuKongIM/WuKongIM/blob/a888f89533d0e7d1b2030e06504ca97f1ad891d4/internal/channel/handler/event_onsend.go)、[存储批处理](https://github.com/WuKongIM/WuKongIM/blob/a888f89533d0e7d1b2030e06504ca97f1ad891d4/pkg/wkdb/wukongdb.go)。仍需实际故障恢复验证，不能凭调用Sync就宣称断电或全链路无丢失。

该版本示例stress模式会强制关闭TokenAuth；对标将采用正常认证与私聊权限，不能直接使用示例压测模式。官方Go SDK默认读/写缓冲各3MiB，10k默认实例内存不可接受；需在适配器显式设置有界缓冲并记录，避免发压端内存耗尽被当成服务端上限。完整业务对标尚未完成，当前没有OpenIM或WuKongIM本机QPS结论。

## 当前传输与 Windows 计时校准

## PERF-019 / 020：真实业务长尾与 Outbox 清理候选
