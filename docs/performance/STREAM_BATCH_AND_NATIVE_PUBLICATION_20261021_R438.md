# 持续收发批量确认与原生发布器配置复盘（R427–R438）

本轮完成了三组各四轮真实 MQ 功能实验，共发布并确认 13,312 条消息；12 轮各刻意漏确认一条，均通过真实重投恢复。每条均核对发布与接收的 Broker ID、topic、tag、key 和完整正文。它们是有限的传输层实验，不是完整 TinyIMX 私聊负载，也没有生成新的整机 CPU、客户端 ACK P99、最大 QPS 或 WuKongIM 追平成绩。

本轮另修正了原生发布器配置入口的缺口，完成普通与 ASan/UBSan 各 75 项配置检查、真实运行模块编译及独立 Message 候选链接。所有产品默认值和现有运行程序保持原样。

## 1. 正常边发边收时，批量确认确实能形成

先前 R235 先发布完 32 条再消费，验证了协议和失败恢复。本轮 R428 让发送和消费同时运行，没有人工处理延迟，也没有先填满消费队列。固定同一个 SDK 候选和相同官方 Proxy 镜像；每轮各创建独立临时 Proxy，仅切换它的 `enableBatchAck`。原 Proxy 配置未改变。

| R428 轮次 | Proxy 服务端批量 | 确认消息 | SDK 多 entry 请求 | 实际 Broker 单条 ACK | 实际 Broker 批量 ACK | 平均接收批次 |
|---|---|---:|---:|---:|---:|---:|
| off1 | 关闭 | 1,024 | 100 | 1,024 | 0 | 10.25 |
| onn1 | 开启 | 1,024 | 108 | 0 | 108 | 9.40 |
| onn2 | 开启 | 1,024 | 109 | 0 | 109 | 9.32 |
| off2 | 关闭 | 1,024 | 100 | 1,024 | 0 | 10.15 |

Broker 请求数来自实际 TCP 重组后的 Remoting 帧，核对了本轮 group，并拒绝丢段、冲突重传和截断。不是用 SDK 函数名推算请求数。所有 ACK 回调均完成后才结束客户端；超过不可见期后再次检查没有返回已确认数据。

结论：即使不预填充，客户端批量请求在持续收发中也能形成，服务端开关决定它是否继续拆成 N 次 Broker ACK。这个机制值得进入完整系统对照；请求数减少不能换算为相同幅度的 CPU 改善。

证据：`PERF428-stream-wire-r1/result.json`、各轮 `parsed-ack-requests.json`、原始 `capture/ack.pcap`、`execution.json` 和 C++ 断言源码。

## 2. 发送计划校准没有通过，保留负结果

R428 计划以 1,000 条/s 发出 1,024 条，但四个同步发送线程平均落后计划 278–301 ms。故本轮没有把该探针称为合格的 1,000 条/s 稳态负载。

R430 先让 128 条预热消息边发边收，全部确认后再释放后续 1,024 条计划流量；稳态阶段依然没有预填充。四轮均未通过事先写入代码的发送节奏检查：平均滞后不超过 5 ms、P99 不超过 10 ms、最大不超过 25 ms。预热后的平均滞后依次为 123.00 / 299.39 / 45.52 / 191.65 ms。因此，冷启动不足以解释全部滞后。

随后 R432 固定服务端批量开关为关闭，在同一个可执行文件内只改变同步发送槽位 4 / 16 / 16 / 4。下表是该受限传输探针的观测，不是客户端持久化 ACK 延迟，也不是正式 IM 性能对比。

| R432 轮次 | 同步发送槽位 | 发送起点滞后均值 | 同步发送调用均值 | 同步发送调用 P99 | 节奏检查 |
|---|---:|---:|---:|---:|---|
| off1 | 4 | 131.44 ms | 4.28 ms | 59.03 ms | 未通过 |
| onn1 | 16 | 13.05 ms | 11.53 ms | 62.74 ms | 未通过 |
| onn2 | 16 | 107.74 ms | 15.23 ms | 79.55 ms | 未通过 |
| off2 | 4 | 220.25 ms | 4.67 ms | 59.99 ms | 未通过 |

增加槽位减轻了本探针的计划排队，但单次同步调用变慢，且没有通过全部节奏检查。两轮/模式也不能证明稳定收益；不据此将产品线程数提高到 16。

R434 随后读取仍在运行的本轮临时 Proxy：其 `cpu.max=200000 100000`，观测开始前累计已发生 24 次限流；观测期间该计数没有增长，OOM 为 0。这只证明这个限定 2 CPU 的功能仪器曾触发限流，未将每次发送与限流时间对齐，不能断言全部滞后由它导致。实际原 Proxy 为 `cpu.max=max 100000`，没有这一 CPU 配额，累计限流为 0。不能把受限功能探针的发送等待当作当前生产候选的等待根因。

下一验证：完整对照采用原服务资源约束、Windows 发压和相同业务语义；实际记录发布排队、同步调用、后台排空和消费批次，不将本轮短探针的请求数或时间替代整机结果。

## 3. 已核实并落实的代码修正

现有实验身份中的 `relay_override.workers=8` 指向独立 SQL Outbox relay，不能证明原生 Message 内的发布器用了 8 个 worker。原生发布器与 SQL relay 分别配置是合理的隔离边界；需要纠正的是配置入口和实验记录中没有明确区分它们的问题。

本轮新增 `NativePublicationPolicy.h`，并接入 `NativeMessageRuntime`，支持原生 owner 文件中的独立配置：

```json
"publication": {
  "workers": 4,
  "max_held": 64
}
```

- 缺省仍为 4 / 64，SQL relay 设置不会隐式改变它。
- worker 支持 1–16，持有事件上限支持 1–256，且不得小于 worker 数。
- 拒绝浮点数、布尔值、字符串、负数、零、溢出值、未知字段和不一致容量。
- 在建立原生 owner、打开本地存储或创建 MQ 客户端前解析，参数错误提前失败。
- 启动日志输出实际 worker 和持有上限，便于后续实验核对真正生效的参数。

## 4. 既有 CPU 证据的可用范围

R431 重新归档了 R397 的全部 149 个 Proxy Java ExecutionSample 和 146 个 Broker Java ExecutionSample，逐条保留时间、线程、状态和完整栈；均未报告截断。Broker 的 TimerFlushService 栈为 33 个，其中 TimerWheel.flush 为 31 个。

NativeMethodSample 与 Java ExecutionSample 分开计数。方法的包含计数会重叠；异步 Netty/gRPC 栈又常常没有业务方法标签。因此，这些样本不能直接换算为 ACK 独占 CPU 或整台 VM 忙核，更不能把 epoll 等待计作 CPU。实际 Message 高负载调用栈仍是未完成项，R422 的新记录器尚未在正式资格通过的当前完整负载上执行。
