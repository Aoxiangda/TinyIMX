更新：2026-10-24。最新R899—R911：真实本地权限异步已实现并通过完整依赖图、内存检查、两组TCP51项及实机SQL在途deadline/停机排空。正式容量/性能主目标继续active；所有候选按同负载A/B决定采纳，详见第10节。

R867 运行分支纠正：保留的 R824 两个网关实际均为 LOCAL_PERMISSION_ENABLE=1、ASYNC_MESSAGE_RPC_ENABLE=0，执行本地权威权限 SQL；本报告早期将远端 Social RPC 源码分支概括为 R824 实际成本，已纠正如下。历史 R863 结果文件保留，路径归因以 R867 实际容器环境、启动注入及调用分支证据为准。

**结论：仍有值得验证的优化空间，但不能把整组性能差异归为某个函数，也不能通过少做业务来获得“追平”。** 已经核实的差异包括进程边界、权限及身份读取、提交粒度、接收状态持久化、未读返回值和后台发布责任。它们中既有保留完整业务所需的工作，也有可能通过异步等待、合并提交或减少重复访问降低的开销。必须逐项隔离验证。

## 1. 性能差距存在，但历史点不能替代新的等价 A/B

下表是已有合格完整点：同一 8 vCPU / 16 GiB 虚拟机、20,000 连接、全部用户参与发送、1,000 消息/s、60 秒、128 字节明文业务载荷、本地用户对投递。两边均 60,000 / 60,000 完整成功并完成历史核对。

| 指标 | Tiny R353 | 固定 peer R46 | 观察到的 Tiny/peer |
|---|---:|---:|---:|
| ACK 平均 | 8.737 ms | 2.157 ms | 4.05 |
| ACK P99 | 27.383 ms | 11.209 ms | 2.44 |
| 计划发送到投递 P99 | 27.612 ms | 14.194 ms | 1.95 |
| 整台虚拟机平均忙核 | 5.826 | 1.739 | 3.35 |

这是系统级历史参考，不能称为本轮候选收益或相邻交替实验。peer 原生单进程、Tiny 容器内多进程；协议、加密和普通接收确认的耐久合同不同。peer 开启消息协议加密，Tiny 对应客户端发送明文，同明文大小不等于同线上字节或 CPU 工作。不能把这些条件隐去后，将 CPU 差值全部称作实现浪费。

固定 peer R77 的 20K / 3,000 消息/s / 80 秒 / 240,000 全量成功，是另一个负载点；不能用它的预声明稳态 P99 与 Tiny 另一负载的冷启动全窗口 P99 直接算性能倍数。

## 2. 真正核实到的业务和实现差异

| 问题 ID | 固定 peer 的实际路径 | Tiny 当前实验链路 | 判断与保留边界 |
|---|---|---|---|
| PERF-863.1 | `onSend → permission → persist → sendack`；存储提案等应用；`AppendLogs → AppendMessages → CommitWait → Commit(pebble.Sync)` 后通知等待者 | 消息、CID、历史/未读/待投递索引及待发布事件一起 WAL 同步写成功，随后才可产生持久成功响应 | **两边都有耐久发送 ACK。** peer 没有靠跳过落盘取胜；可学习其 ready-only 合批，不能关闭 WAL/fsync 或提前成功 ACK |
| PERF-863.2 | 普通 `RECVACK` 移除内存重试项；命令消息/主设备另有异步会话进度分支 | 接收者归属校验后耐久保存确认、移除 pending，确认与已读分开 | 语义不同。不能照搬“只删内存”来替换 Tiny 接收确认；可以合并多个已到达确认，仍等待同一次同步提交成功 |
| PERF-863.3 | 单节点时在进程内查询频道、黑名单/白名单，远端权威节点才走 RPC | R824 实际为 Gateway → 本地权限工作池 → 关系 SQL → future 等待返回；另有 Message RPC 内旧 CID 排序规则/用户存在核验。远端 Social RPC 是另一个可选分支 | 该轮权限阶段没有 Social 网络 RPC 成本。实际存在本地任务投递、SQL及等待；保留权威判断，优先分解真实路径，不能把未执行的 RPC 分支列为瓶颈 |
| PERF-863.4 | 分片本地批次提交；会话更新经 ConversationManager | 本地耐久消息外仍有 RocketMQ 发布、发布进度、未读投影；ACK 还带未读计数读取 | 完整业务成本必须保留。要测前台和后台各自的持续能力，不能暂停 MQ/投影、等发压结束后排空就声称达到该吞吐 |
| PERF-863.5 | 按 peer 自身准入与事件处理运行 | R824 首约 20 秒发生 4,516 次 `overloaded`，后续预声明 90 秒无该类拒绝 | 是实际失败；启动冲击与持续容量要分别定位。历史缺少拒绝子计数，不能硬归因数据库或某个共享队列 |
| PERF-863.6 | 本次 peer 是完整私聊功能测试，但仍为单副本私聊负载 | Tiny 的产品还包含群快照权限、文件、AI/MCP、多会话等，容量点未同时加载这些流程 | **私聊容量通过不等于全部产品业务通过。** 候选必须另过完整业务门禁 |
| PERF-863.7 | 运行时鉴权开启、私聊白名单校验开启；槽/频道各 1 副本 | 原 8C/16G、多服务保持；新实验盘须建立新的公平存储对照 | 单机性能与多副本/高可用分别验证；同配置不自动等于同合同 |
| PERF-863.8 | 有若干已测通过点，不是脱离业务的硬件固定极限 | 有合格 20K/1000 点、失败的更高负载点；没有完整业务最大 QPS 结论 | 以成功率、延迟目标、后台稳定排空、资源和恢复共同定义可持续容量 |

实际 peer `server.yaml`：`tokenAuthOn=true`、`stress=false`、`whitelistOffOfPerson=false`、`slotReplicaCount=1`、`channelReplicaCount=1`。实际保留的 **8 个消息分片 OPTIONS 均 `disable_wal=false`**。`wal_bytes_per_sync=0` 不等于关闭同步提交，提交调用明确是 `pebble.Sync`。进程退出恢复与宿主断电、介质故障仍是不同试验范围。

peer 的内存接收确认不构成“peer 离线不可靠”的结论：其频道消息日志和客户端同步进度可以承担另一种恢复合同。要比较的是用户最终看到的消息、顺序与重试行为，不能单看一个回调。类似地，peer 保存 `ClientMsgNo` 字段不能单独证明其具有 Tiny 的 CID 复用/内容冲突合同；需独立重发测试，不作未经验证的等价声明。

## 3. 当前延迟和 CPU 的原因，哪些已经测到

**已经排除“主要耗在 Windows 入队”这一种解释。** R830 对 R824 的全部 175,484 个成功请求逐条对齐：客户端入队、JSON/发送互斥到 write 标记平均 0.01756 ms、P99 0.0529 ms；write 标记到收到并解析 ACK 平均 140.0356 ms。后一区间仍包括客户端 socket、网络、服务器和返回处理，不能直接称为纯服务器耗时，也不能从两个独立 P99 相减归因。

**后台确有积压，但尚不能把积压全部定位为一把锁。** R840 对同一批已接受 MID 核对：

- 事件产生到 SDK `born`：平均 19,340.779 ms，P99 30,576 ms。
- SDK `born` 到 Broker 存储：平均 1.362 ms，P99 6 ms。
- 120 秒 offered 窗口内 Broker 只存入约 130,136–130,523 条，即约 1,084–1,088 条/s；最终 175,484 条均排空不等于持续承载 1,500 条/s。

第一个区间包含本地提交、待发布排队、领取、准备、调度和重试等，尚未逐段完整拆开。它与前台 ACK 并非串行累加关系，不能把约 19 秒直接加到 ACK 延迟。SDK/Broker 区间较短说明应优先拆查进入 SDK 之前的工作，仍不能据此断定 Broker 永远不是瓶颈。

**拒绝和资源干扰必须保留。** R824 共 180,000 条计划，175,484 条完整成功，4,516 条拒绝（2.5089%），发生于第 1.4973–19.9347 秒；宿主内存和根盘门槛也未全部满足，不能作为干净的最大容量实验。该轮数据核对证明负 ACK 未被错误持久化，以及成功集合最终一致；它不能把失败的容量结果改成通过。

历史按 MID 暖路径采样确有业务队列、权限、Message RPC、本地同步写及未读读取时间；样本均值和嵌套区间不能冒充全量 CPU 占比。全虚拟机忙核也不是 Gateway Reactor 自身忙核。未取得干净单因素结果前，不将差距归咎于 C++、epoll 或虚拟网卡。

## 4. 本轮确实执行的业务验证：R864

新建 `native_confirmation_rpc_parity_test.cpp`，经过真实回环 gRPC、实际 `MessageServiceImpl`、`MessageApplicationService`、原生仓库及未读快照服务。相同程序分别运行确认合批关闭、开启，比较规范化业务结果及重新打开后的存储状态。

Release 和 ASan/UBSan 两种构建均通过，共 16 个编译/链接/运行步骤；两种构建的规范化结果也一致：

| 对外行为 | off/on 结果 |
|---|---|
| 同 CID、同内容重试 | 同一 MID，返回复用 |
| 同 CID、内容冲突 | 返回明确冲突，原消息不变 |
| 错误接收者确认 | `PERMISSION_DENIED`，无状态变更 |
| 未知 MID 确认 | `NOT_FOUND`，无状态变更 |
| 首次确认 / 重复确认 | 影响 1 行 / 0 行 |
| 接收确认后未读 | 仍为 1；没有混为已读 |
| 已读后迟到确认 | 影响 0 行，状态不回退 |
| 24 个并发单条确认 RPC | 每条只变更一次，pending 最终为 0；24 条仍保持未读 |
| 随后标记已读 | 精确变更 24 条，未读为 0 |
| 历史与重新打开后的记录 | 25 条记录逐条一致，全部保留 Read 状态；无 SQL 空结果兜底 |
| 关闭 owner 后请求 | 明确 `UNAVAILABLE`，快照不伪造成功空结果 |

该测试是独立身份夹具，**没有测试 SQL CID 规范化、Gateway 登录/SessionEpoch、真实群/文件/MCP、MQ 发布、Redis 重建或完整系统故障**。真实同步写前后 SIGKILL 的证据另在 R854；本轮仅正常关闭/重新打开，不冒称再次测了进程崩溃。

## 5. 后续优化的准入条件

新确认合批、权限异步等候选继续独立且默认关闭，原服务不替换。按以下顺序推进：

1. R866 已完成新完整 Gateway 的可追溯构建与镜像加载。接下来只在隔离新夹具中固定全部二进制、SDK、配置及数据所有者，跑完整 TCP 私聊/跨网关双向 FIFO、重复 CID/冲突、丢失 ACK/重连/退出恢复。
2. 跑完整权限矩阵：双方拉黑/删好友、旧连接替换、权限服务失败，以及群退出/后入群历史 ACL。按项目已有在途请求合同验收，不能擅自把已经接纳的 MustRun 耐久写变成取消，也不能把旧连接当当前会话回复。
3. 完成 MQ/Redis 全量闭环、故障后重建、在途优雅停机，并补共享网关调度下的文件取消/完成与 MCP 身份回归。
4. 新实验卷校准后，先复现资源合格的基准，再分别只切持久化异步、已测明的本地权限等待优化、身份缓存、接收确认合批。远端权限 RPC 异步按另一种实际部署分支独立验证，不能混入本地权限基准。每轮保留完整成功率、ACK/投递、逐段等待、线程 CPU、整 VM CPU、实际批大小和后台积压。
5. 同窗口刷新固定 peer。按预声明方式逐级增加用户数、活跃比例和速率，同时报告均匀/热点、同/跨网关、会话读取与后台投影。完整业务持续容量和私聊交集参考分别展示。

任何成功 ACK 丢消息、未授权访问、顺序回退、已读回退、未读不一致、后台持续增长或停机无法排空，都直接拒绝该候选，即使某项 P99 更低。异步化可能增加在途并发和下游压力，合批也可能增加等待，均以真实业务合格后的 A/B 决定保留，不预先承诺追平倍数。
