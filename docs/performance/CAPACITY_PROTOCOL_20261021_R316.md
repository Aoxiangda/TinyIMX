# 当前冻结版本的容量与对标协议

硬件固定为原 Ubuntu 8 vCPU / 16 GiB，Windows 原生发压；保留用户工作窗口、原业务数据库、指定旧测试库、容器、镜像和快照。空间不足时先转存可恢复的已结束测试证据，不以降低资源门槛换取成绩。当前重新获得清理授权，R304/R312已完成实际E恢复及Linux引擎恢复验证后冷存档。

## 不能把连接数当吞吐上限

分别测量连接承载、登录速率、私聊持久化ACK、实际唯一投递、会话/历史查询、群投递、文件和AI工具调用。每个QPS都必须附操作、正文大小、活跃比例、热点分布、持久化/确认合同；群发送QPS与接收者投递条数分列。登录爬坡100/s是限速设置，不是登录能力上限。

R309四轮700消息/s对照各42000完整成功，两个方向ACK P99降低10.09%/11.87%，忙核降低3.53%/2.43%。保留按空位限页进入更高负载候选，不改原生产默认，不把两对结果称为所有负载下最优。相同九程序、index1/held0/empty0固定；后续SDK因素独立测量，最后验证组合。

700/s开启组约5.04–5.06忙核，相当于每完成消息约7.2ms的**整机CPU时间预算**，其中包含后台和观察开销。若局部近似按同样工作量线性增长，8核预算交点约1100/s，仅用于选择下一档1000/s；不是最大QPS结论。后台基线、合批、锁竞争及饱和后排队都会破坏线性关系。固定WuKongIM历史700/s约0.95忙核，也不能线性外推成其已实现容量。

既有回显校准R18/R19为10000活跃连接、256B、计划600000次/60s：Muduo收599998、Tiny适配器收599996。它们表明当时传输/发压路径能提供接近10000次/s字节回显，不证明完整IM容量，也没有证明当前环境的传输上限。R16闭环大包有效载荷约1.018Gbit/s/方向，同样不是持久化消息QPS。所有原始失败/跳过数保留。

## 发送速率边界

1. 新r3161范围先测1000/s、60s、60000新消息、10000认证连接、全部参与、128B、双Gateway本地配对，关闭逐消息诊断。沿用已验证R8、相同九程序和完整MQ/Redis链。
2. 按结果选择1500/2000/3000/5000/8000等更高档位；首次失败后在相邻通过/失败区间缩小到约10%范围，再至少三次复验。它是待执行阶梯，不是达到的数字。
3. 每档使用独立空消息历史及唯一CID；按原始QPC计算负载窗口内ACK与投递完成率，完整计划数、实际发送、负确认、超时、跳过、重复及尾部排空分列。不能用“包含排空的完成数/60s”冒充窗口内吞吐。
4. 初始可用性门槛沿用项目100ms持久ACK P99，另报从发送计划计时的P99、调度迟到和负载窗口内至少95%完成；原资源8GiB/10s启动、6GiB期间、guest零swap、磁盘预留及持久化配置保持。
5. 可用性门槛通过不等于开源性能对齐。固定WuKongIM必须在相同速率、正文、活跃度、连接和空历史条件下记录全量历史/内容、持久化语义、窗口内完成、P99与整机忙核。原生进程与容器桥接、接收ACK持久化及后台架构差异明确列出；不能使用0veth比值或旧500/s的4.84ms混作新对照。
6. 60秒只作粗定位，最终上限候选需10分钟及小时级稳定测量、积压有界和故障恢复。现R8每轮500000计划数上限、Windows端口及内存开销需要在更长/更大规模前完成扩展及发压端资格；工具上限不能作为服务器上限。

## 连接规模与完整业务

新建且核验独立用户范围后测试20K、30K、50K及必要边界。原R8只覆盖10K；R325已实际建立20K Windows独占源端口连接（两个端点各10K），R326/R331/R338已验证扩展客户端的真实协议和失败分母。源端口从10000–49151中选择当前未占用项，使用SO_EXCLUSIVEADDRUSE，未修改系统动态端口、路由、NIC或VM配置。R323/R332分别使用20K独立账户和20K定向关系，账号未复用。30K/50K仍待扩展与验证。

每个连接档分别测在线保持、指定活跃负载、热点/跨Gateway、重连与离线恢复；之后测会话/历史、群规模、文件及AI交叉。任一项目未测均保留未完成状态。文件使用字节吞吐/恢复成功，AI区分首token/完成/工具权限，不混成消息ACK。

## 已执行的1000/s及20K分支（R316—R349）

10K、1000/s、60秒的R316完成60000条全链收尾，ACK均值7.848260ms/P99 24.1472ms，计划至投递P99 24.5507ms，整机平均5.772093忙核。窗口内ACK/投递59994条，即999.9/s；包括排空的60000不是窗口内吞吐。宿主最低6.4065GiB、guest零swap，当前这是通过资源资格的工作点，不是最大QPS。

第一轮20K（R323，原16KiB读缓冲、默认Go GC）60000条业务、FIFO、索引、逻辑引用、实际MQ及40000个Redis键全部正确，但负载内宿主最低5.0579GiB，低于6GiB。34.6244ms ACK P99及5.9103忙核仅保留为资源不合格观察，不能作为正式容量。

第二轮20K（R332，2KiB缓冲、GOMEMLIMIT=384MiB）负载内宿主最低6.5263GiB，却出现15357条明确overloaded拒绝，44643条成功。客户端累计CPU1485.703秒、宿主负载均值92.32%，均显著异常；低内存上限候选拒绝，原始失败保留。不能将成功子集的P99代表60000条请求，也不能将guest忙核下降误报服务器优化收益。现有证据支持发压端GC/调度严重干扰这一方向，未采集GC调用栈，不给出GC精确占比。

R337对失败轮继续完整审计：44643条正确认全部持久、接收确认及投影正确，15357条负确认CID在完整M/I/A集合中均不存在，无待投/隔离/孤儿引用或Retry/DLQ。Redis的258个零总数键允许不存在，未漏查正值。这是过载拒绝及接受子集可靠性的证据，未将失败轮改判成性能通过。

下一轮R339保持全部九个服务程序及服务端配置，仅用2KiB读缓冲并恢复默认GOGC=100、GOMEMLIMIT unset；已完成协议测试和r3391空历史夹具，仍受原8GiB/10秒与负载6GiB约束。资源等待不计服务器失败或容量，也不通过降低门槛进入负载。

固定WuKongIM的20K客户端已用setup-only SDK Dial钩子实现同一独占端口策略，消息/加密/ACK路径保持原R5。R347四用户20条实际收发通过，继承的QPC与Go原生时长差<1ms断言失败；R348独立50500次校准证明QPC与Tiny及Python处于共同计时域，同时Go原生时间存在离散步进。独立诊断未完整解释此前2.5817ms最大差，保留异常。R349在正常重开同一固定Peer后逐条核对20条CID/MID/明文历史一致，未产生新IM消息。此功能资格不构成20K性能成绩，历史700/s点也不能与1000/s直接作比例。

## 源码优化与最终验收

每项改动必须有固定开源源码锚点、Tiny实际差异、单变量前后完整数据及失败恢复证明。当前额外解码已被消除，网络边界和调度工作量仍高；下一项独立实验是实际多entry MQ ACK，而不是仅并发N次ACK。若收益不足，继续按每角色CPU、调用次数、锁/队列及提交证据选择结构改动，保留所有负结果。

“最佳”最终应表述为给定版本/部署/负载和可靠性合同下，经边界与持续验证的性能。不能把单点通过、CPU线性预算、静态代码审计或“差距有解释”当作已经追平。整体目标继续包含高质量开源对齐、服务器持续容量和全部故障/权限语义。
