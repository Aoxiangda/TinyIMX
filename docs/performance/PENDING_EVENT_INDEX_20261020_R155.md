# 非空待发布索引：源码、机制消融与工程资格

当前状态：候选默认关闭。九个程序已构建并通过实际角色镜像的加载检查；基础契约、内存检查、并发/重启/预算测试和四次真实终止恢复通过。局部机制成本显著下降，完整系统的 CPU、ACK 和容量收益尚未验证。

## 由前项负结果触发的假设

PERF-148 实际调用栈显示 `LocalEventRelay::Poll → ListPendingEventsAfter → RocksDB iterator` 的重复扫描。PERF-149 只在待发布计数为零时跳过查询；完整负载两轮 ON 仍执行 62030 / 63416 次扫描，整机均约5.44忙核，未见稳定收益。第四轮 OFF 虽通过完整后端，主机内存最低5.4029GiB，被原6GiB门槛拒绝。保留该拒绝，正式ABBA未完成，空保护默认不推广。

新假设：即使队列非空，也无需反复越过已经删除的历史内部键。按照已提交待发布键定位正文，能够消除这项与历史删除数量相关的扫描成本。借鉴固定 Peer 的“对已就绪工作推进”的原则，保留 Tiny 当前的持久化/MQ/Redis职责，没有复制未经适配的接口或省略后台链。

## 单项实现

开关 `TINYIMX_NATIVE_PENDING_EVENT_INDEX_ENABLE=1`，默认0。单独的空队列保护开关在本项对照中固定0。

- 内存只保存有界事件键及就绪标志。`E/` 仍是权威持久化索引，正文仍通过 RocksDB 的一致快照点查并验证原有事件编码。
- EventSlot 在落盘前分配、登记未就绪节点。同步写成功后，以无分配的原子标志发布就绪状态，再使用原通知流程。写失败会释放预留；不改变存储不确定失败后的 poison/fence。
- 查询在短锁内选取已经就绪、严格大于游标的键，释放锁后读取正文。索引锁不跨越引擎操作。并发发布使选中键消失时正常跳过，保留原 relay 的 held 所有权与循环处理。
- 发布或隔离只有在原持久化变更成功后才移除内存键。重新入队先预留、写入成功再就绪。重启从真实 E/ 重建，不把进程内状态当作恢复依据。
- 索引受既有 `max_pending_events` 预算约束。如果配置缩小后，原合法积压超过新预算，则在启动时回退到原扫描路径；不超预算构建索引，也不阻止旧积压继续处理。
- 不改变 format=3、消息/CID/未读/投递/确认索引、SQL引用、WAL、同步写、MQ发布、重试、隔离、接收端确认或停机边界。

## 局部机制结果

同一个可执行文件，四个全新空间。每轮同步创建4000条消息，完成3999个事件的发布进度后，保留排序末尾1个真实待发布事件；查询2000次，核对返回事件ID与完整正文。另一项空队列开关固定0。

|顺序|键索引开关|实际迭代扫描|索引点查次数|进程CPU ms|墙钟 ms|
|---|---|---:|---:|---:|---:|
|1|OFF|2000|0|404.421|404.579|
|2|ON|0|2000|13.426|13.430|
|3|ON|0|2000|13.031|13.035|
|4|OFF|2000|0|418.881|418.925|

这是固定非空查询的机制实验，约31倍的进程CPU成本差异不代表整机CPU或吞吐提升31倍。测试中的积压分布与真实负载不同；完整负载必须另测。

## 已执行的工程验证

原 store / relay 的 OFF、ON、Release 和 ASan/UBSan 共8组通过。新增机制测试也在 OFF、ON 的 sanitizer 程序下通过，覆盖：

- 非空事件的正文、顺序、严格游标、非法游标与关闭栅栏。
- 隔离、重新入队及事件正文逐字节保持。
- 较早MID在写前暂停，另一对用户较晚MID先提交：未提交节点不可见，较晚已提交节点可见，较早提交完成后不会遗漏。
- 猜测尚未提交的事件ID进行发布确认时，零受影响行不能误删其未来索引节点。
- 关闭后以更小预算重开：旧积压仍可处理，超预算新增被拒绝；处理后恢复准入；恢复原预算重开能重建剩余 E/。

四个实际 SIGKILL 位置及恢复均通过：写前、同步写后回复前、发布成功但进度尚未保存、隔离完成后。[资格结果](../../benchmark/results/peer-20261017/PERF155-pending-index-qualification-r1/result.json)。九个新产品完成构建；只有 Message 的字节发生变化，其他八个产品与R150哈希相同。2194个容器与保护库行数保持不变。
