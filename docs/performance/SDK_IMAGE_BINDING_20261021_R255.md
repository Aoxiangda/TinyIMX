# SDK 候选被镜像旧库遮蔽：实证、修正及剩余接入

2026-10-21。PERF-255/256确认了实际镜像中的库选择差异。此项修正正式比较的有效性，没有产生新的完整性能成绩，不能归因既有5.44核与0.95核的差距。

## 已确认的问题

三个MQ角色的候选ELF均依赖 `librocketmq.so.5`，RUNPATH指向固定的主机SDK目录；原角色环境却包含 `LD_LIBRARY_PATH=/opt/tinyimx/lib`。镜像中该目录也有旧SDK。动态加载器优先使用后者，因此只把新SDK挂到RUNPATH目录仍可能被旧库遮蔽。

旧R212冻结控制器还把SDK路径固定为原版，并只对Message/未读投影添加SDK挂载，遗漏了同样依赖SDK的outbox-relay。原R175/R212文件保持冻结；不能把新候选包直接套入原控制器后宣称已使用新库。

R255重新检查E中实际恢复的R247全部18份loader日志：其中6项具有MQ依赖，覆盖三角色各自old/wire标签，**全部解析到镜像 `/opt/tinyimx/lib/librocketmq.so.5`**。因此旧检查只证明依赖/ABI可加载，不能证明新候选SDK被选中。这纠正了先前加载验收的范围。

SDK/Main在宿主侧运行的R223/225/228/243/248实验显式设置了候选库路径并做相应能力检查，不因本次容器加载问题被否定；仍不能把它们当作正式容器完整链结果。

## 已落实的绑定代码

`benchmark/peer_compare/frozen_sdk_binding_r255.py` 为三个MQ角色统一生成只读SDK挂载，并将固定挂载目标放到LD_LIBRARY_PATH首位；保留其余依赖路径，禁止当前目录搜索与重复环境项。原版/新版使用相同加载路径布局，库源及SHA是明确变量。

日志候选开关固定0，线协议ACK开关只在未读投影显式启用；原版或OFF使用0。SDK批量开启仍另需应用ACK批量开关，不能混同。代码核对实际挂载源、目标、只读属性、选中库路径和SHA，而非只看启动命令或可加载状态。

这是已在实际镜像验证的绑定组件，**尚未接入并执行完整SDK性能控制器**。下一项是将该组件加入独立SDK控制器，在首次停止原服务前完成相同加载核验，并在正式角色启动后、放行流量前再次核对实际映射库/环境与投影统计能力。不得修改原R175/R212控制组来省略独立变量。R232/R251包字节继续保留，但部署必须遵循此绑定约束，原先仅依赖挂载约定不足。

## 夹具失败及修正

R256r1最初错误推断“原Message程序ldd无MQ依赖→镜像里没有MQ库”，负向控制却真实选中镜像旧库，断言失败。该容器已在finally停止删除；失败日志和原脚本保留。第一次实际SHA尚未在断言前保存，不补造；R2改为先保存完整观察，再验证三个角色，最终表格全部以R2独立观察为准。没有运行或重放IM消息。

R254首次清理预检误用了 `positions_unchanged` 字段名，真实证明字段为 `offsets_unchanged`；删除前停止。独立列举确认所有目标仍在，修正字段后在新r2范围重新核对E归档、实际恢复文件、全部源SHA、终态及所有2292挂载，才精确删除18份结束的原始Broker分析映射，28,852,326字节。18份最终验收摘要留guest，原始文件完整留E。程序、缓存、数据库、原生owner、binlog和容器不在删除范围。

## 性能主线仍未完成

R253宿主连续10秒可用4.983—5.030GiB，未达原8GiB正式启动门槛，正式目录仍不存在；guest swap0，无遗留测试进程。各资源/源码/失败/对照项均登记问题台账。没有因这一实际路径缺陷就宣称找到全部CPU原因，也没有将9个加载夹具或请求计数换算为IM吞吐/P99收益。

资源真实满足原门槛后，先完成R175/R212限页控制；SDK独立阶段先做原版与同候选OFF兼容控制，再做同候选OFF/ON/ON/OFF，服务端batch固定false。后台全量事件/Redis/Retry/DLQ、顺序、权限和持久化ACK边界通过后，按整机忙核与Windows端到端P99决定是否保留；服务端批量另作独立变量。

R258在九个临时加载夹具均结束并回收后，再独立连续10秒检查宿主可用4.960—4.996GiB，仍未达原8GiB门槛；正式目录不存在，未启动正式驱动。
