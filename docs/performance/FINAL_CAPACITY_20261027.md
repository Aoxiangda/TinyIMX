# TinyIMX 50K 用户容量与消息吞吐实测

TinyIMX 在 8 vCPU、16 GiB Ubuntu 虚拟机上，完成了 50,000 个认证在线用户下的两档私聊负载：1,000 条/秒与 1,250 条/秒，各持续 300 秒。两轮共 675,000 条计划消息全部完成持久化、接收与确认，独立核验正文及全部关键索引，收尾时待发布事件与待确认消息均为零。

本次发布采用这两个已完成工作点，日期为 2026 年 10 月 27 日。连接规模、消息 QPS、正文吞吐、延迟与持续时间共同描述结果。

## 正式结果

共同条件为 50,000 个认证在线连接、128 B 正文、300 秒；全部 50,000 个账号在窗口内参与收发。

| 业务消息 QPS | 完整成功消息 | ACK 平均 ms | ACK P50 ms | ACK P99 ms | 计划到投递 P99 ms | 虚拟机平均忙核 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 300,000 / 300,000 | 9.258 | 6.771 | 48.573 | 49.596 | 5.606 |
| 1,250 | 375,000 / 375,000 | 13.290 | 9.870 | 60.553 | 61.891 | 5.719 |

两轮负 ACK、超时、无效内容、原始重复投递和未调度消息均为零。每轮通过首次未读投影校验，后台待发布、隔离及待确认工作归零，原服务和受保护数据恢复校验通过。

## QPS 与正文吞吐计算

一条业务消息包含发送、持久化 ACK、接收投递、接收确认及后台派生处理。QPS 按业务消息计算；心跳、RPC 与 MQ 内部操作不累计为额外消息。

```text
发送 QPS = 计划发送消息数 ÷ 300 秒
完整完成 QPS = 完整成功消息数 ÷（300 秒 + 最后消息收尾时间）
正文吞吐 B/s = 窗口内实际投递消息数 × 128 B ÷ 300 秒
MiB/s = B/s ÷ 1,048,576
Mbit/s = B/s × 8 ÷ 1,000,000
```

| 发送 QPS | 含收尾的完整完成 QPS | 按发送速率折算 B/s | MiB/s | Mbit/s | 窗口内实际正文 B/s |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 999.978 | 128,000 | 0.122070 | 1.024 | 127,997.440 |
| 1,250 | 1249.946 | 160,000 | 0.152588 | 1.280 | 159,991.467 |

1,000 QPS：300,000 ÷ 300 = 1,000；正文约 128.000 KB/s、0.122070 MiB/s、1.024 Mbit/s，合计完成正文 38,400,000 B。

1,250 QPS：375,000 ÷ 300 = 1,250；正文约 160.000 KB/s、0.152588 MiB/s、1.280 Mbit/s，合计完成正文 48,000,000 B。

含收尾的实测分母分别为 300.0067414 秒和 300.0128763 秒。表中实际值保留窗口末尾极少量跨界完成的差异。KB 与 Mbit 采用十进制，MiB 采用二进制。以上为消息正文的单份有效吞吐；网络总流量还包含帧头、TCP/IP、ACK、RPC、MQ 和心跳。

## 测试环境与业务路径

| 项目 | 配置与范围 |
| --- | --- |
| 服务端 | Ubuntu VMware 虚拟机，8 vCPU，16 GiB |
| 发压端 | Windows 原生 TIMX 协议客户端，与虚拟机共用物理宿主机 |
| 连接与认证 | 50,000 个真实 TCP 认证连接；15 秒心跳 |
| 服务部署 | 同一虚拟机内的双 Gateway、五业务服务、文件入口、MCP、发布器、投影及依赖 |
| Gateway 路径 | 两个 Gateway 均衡承载，每对私聊用户位于同一 Gateway；跨 Gateway 正确性另由业务套件验证 |
| 私聊存储 | Native 原子提交，同步 WAL；消息、CID、历史、未读真值和待发布事件同时提交 |
| MQ | RocketMQ LOCAL，SYNC_FLUSH；Proxy 与 Broker 为同一物理进程 |
| 发布器 | 8 工作线程，最多 64 在途，进度批次 16；MQ SEND 逐条发送 |
| SQL 与 Redis | MySQL 保存账号、关系、群、文件及逻辑引用；Redis 保存路由与未读投影 |
| 测试正文 | 每条 128 B，固定可校验正文 |
| 用户活动 | 按账号轮转；全窗口参与，不表示每个用户每秒都发消息 |

1,000 QPS 对应平均每用户每分钟 1.2 条；1,250 QPS 对应 1.5 条。50K 连接约产生 3,333 次心跳/秒，心跳不计入业务消息 QPS。

## 延迟与资源

ACK 从客户端进入发送队列计时，到客户端收到持久化确认结束。计划到投递从预定发送时间开始，到接收端完整校验消息结束。P99 根据全部消息的原始逐条记录计算，首分钟和慢请求保留在完整窗口中。

| 测量分钟 | 1,000 QPS ACK 平均与 P99 ms | 1,250 QPS ACK 平均与 P99 ms |
| ---: | ---: | ---: |
| 1 | 17.754 / 84.841 | 22.788 / 88.179 |
| 2 | 7.112 / 28.689 | 10.332 / 38.564 |
| 3 | 6.956 / 25.470 | 11.067 / 42.094 |
| 4 | 7.217 / 30.726 | 11.806 / 47.349 |
| 5 | 7.252 / 27.200 | 10.459 / 38.884 |

两个工作点首分钟的 P99 分别为 84.841 ms 与 88.179 ms，均高于随后各分钟；报告仍使用完整 300 秒的 48.573 ms 与 60.553 ms。P99 表示 99% 消息达到的延迟分位，仍有更慢请求；两轮 ACK 最大值分别为 208.939 ms 与 194.833 ms。

对当前发布，1,000 QPS 工作点拥有较低尾延迟；1,250 QPS 提供更高完成速率。二者均保留完整持久化与确认语义。两轮客户端的心跳调度版本不同，因此它们用于展示各自条件下的容量，不据此计算某一项服务端优化收益。

整台虚拟机平均忙核分别为 5.606 与 5.719，约为 8 个 vCPU 的 70.08% 与 71.48%，包含业务、依赖和操作系统开销；实际采样覆盖分别为 298.529 秒和 299.533 秒。两轮虚拟机换入换出页数均为零，宿主机最低可用内存分别为 6.598 GiB 与 6.366 GiB。

## 消息完整性与工程能力

每轮完成后关闭写入，独立只读校验器逐条读取持久状态，验证成功消息正文、CID 与 MID 关联、发送接收归属、历史、未读与待处理索引及接收确认。300,000 条与 375,000 条成功记录分别全部落盘和确认；校验前后存储文件 SHA-256 一致。首次未读投影使用实际快照检查，收尾时全部待处理工作闭合。

这些结果对应同一组服务端程序。系统同时提供好友与群权限、群历史 ACL、分块文件完整性和接收者授权、Qt 6 原生客户端、Ollama 流式问答及 8 个受控只读 MCP 工具。容量数据测量私聊路径，其他功能的正确性覆盖见[工程迭代复盘](ITERATION_HISTORY_20261004_20261027.md)。

当前采用 Native 私聊配置；默认 SQL 私聊配置的存储路径与性能数字分别管理。业务层使用逻辑引用与事务维护数据一致性，发布数字不跨存储配置套用。
