# TinyIMX C++后端项目简历描述

TinyIMX 是以 C++ 和 Linux 为基础的即时通信后端。当前适合突出万人指定混合测试、持久化消息链路与有实测对照的优化；五万用户全部功能的低延迟能力属于后续验收目标。

## 可直接使用的项目描述

**TinyIMX 即时通信后端**

技术栈：C++、Linux、TCP、gRPC、MySQL、Redis、RocketMQ、Docker Compose。

- 实现登录、私聊、群聊、会话未读、历史消息、好友与群权限、文件续传等功能，使用 gRPC 拆分业务服务，结合 MySQL 持久化、Outbox 与 RocketMQ 推进消息投递；通过幂等键、租约和接收端 ACK 校验跨 Gateway 的消息与最终状态。
- 采用有界业务执行器和同键 FIFO 调度，以 SessionEpoch 识别失效连接，区分可取消任务与必须完成的任务，覆盖过载拒绝、会话替换、投递确认和优雅停机等边界。
- 在 8 vCPU、约 16 GiB 的 VMware 开发环境中，完成 1 万认证 TCP 长连接的 60 秒指定混合压测：私聊 100 条/s、50 项会话页 20 次/s，并加入两人跨 Gateway 群投递与功能交叉回归；两轮开启优化的私聊 ACK P99 上界最高 57.5 ms，会话页 P99 最高约 38.3 ms。
- 将 50 项会话未读读取从逐项连接租借与 PING/GET 改为有界批量读取，保持授权、精确 int64 计数与原错误语义；同程序开关对照中，网络命令由 100 次减至 2 次，指定万人混合场景会话页 P99 保守降低约 80.46%，逐消息核对实际投递与 SQL 持久状态，并保存 Git、失败样本与恢复记录。

项目日期、个人职责、仓库公开链接应使用本人实际信息填写；以上文字不暗示独立完成所有原始代码。

## 面试时说明测试条件

“1 万”表示实际认证 TCP 长连接数，不是每秒 1 万次请求。主要私聊和会话页负载持续 60 秒；群投递为两人群、2 条/s、60 条正式消息的低样本补充，不能将其经验分位数扩展为大群总体 P99。两个 Gateway、数据库、队列、监控及负载工具运行于同一开发虚拟机，性能结果不等同于独立负载机或生产部署。

57.5 ms 与约 38.3 ms 来自后续提交唤醒对照的两轮开启配置，分别取两轮较高值。80.46% 来自此前未读批量读取对照，计算为 (232.961 − 45.531) / 232.961；它与后续唤醒测试是不同实验，不能合并为同一轮的前后提升。

跨 Gateway 最终确认、幂等负例和权限校验已验证；故障、跨端、TLS、长稳态和所有接口高并发覆盖须分别说明。Outbox、重试和幂等处理不能宣传为已证明任意故障下端到端 exactly once。

## 可以深入讲解的工程问题

原会话页对最多 50 个已授权会话逐项取得 Redis 连接、健康 PING 并读取未读数，等待成本被放大。改为一次连接租借、一次健康检查和一次有界 Lua 执行；Redis 内部仍执行 50 次 GET，因此网络命令减少不等于 Redis 内部读取数量减少。保留精确整数和 wrongtype 等错误语义，并验证 TTL、错误、重复项及并发行为。

消息的发送确认、实际收件、已读可见和持久化完成是不同指标。压测通过实际 MID、收发身份、wire 观察和最终 SQL 状态对账；平均变快仍需检查尾延迟、失败与积压。增加 Message RPC 轮询线程的候选虽然正确性通过，却没有稳定缩短群全部送达，因此没有启用该配置。

同键 FIFO 保护顺序，也可能使共享工作线程受慢 RPC 和热点分条影响。当前执行器持续排空同一分条，公平性是后续需要验证的候选；必须同时检查同键顺序、无丢唤醒、过载和停机，不能仅凭源码断言它是全部尾延迟根因。

## 暂不使用的表述

“支持 5 万用户全部功能极致性能”“所有接口 P99 小于 100 ms”“生产级高可用”“零丢失零重复”“行业领先”“百万 QPS”均不使用。20k 指定场景中私聊 ACK P99 上界约 201 ms、会话页 P99 约 155 ms；100 人群低并发测试的全部送达平均仍约 126–135 ms，AI 完整调用仍为秒级。这些问题适合作为正在定位和迭代的案例，不能写成已完成的成绩。
