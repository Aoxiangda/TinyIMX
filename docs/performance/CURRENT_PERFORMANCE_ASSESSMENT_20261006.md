# TinyIMX 当前性能、功能覆盖与竞争力评估（2026-10-06）

本报告响应用户要求的最终现状审查。结论：项目具有可复核的性能优化成果和较丰富的正确性验证，已经通过指定 10k 在线混合场景；尚未达到 10k–50k 全部功能、各种交互均具有优秀性能的目标。100ms 是现有验收门槛，不能据此称为极致性能。当前不进行新的容量压测、不修改运行配置、不清理其他应用或文件。

截至本报告，Ubuntu VMware 为 8 vCPU、15946MiB 内存，CPU 型号由虚拟机报告为 i5-14600KF。19 个项目容器运行，设有健康检查的容器为 healthy；本次只读快照 MemAvailable 8805MiB、已使用 swap2527MiB。swap 存量不等于当前持续换页，既有20k测试可用内存最低约8.165GiB、未见内存PSI压力，不能把延迟统一归因内存不足。服务、数据库、MQ和负载客户端同机，宿主其他应用继续运行，不能将结果视为隔离专用服务器的硬件上限。

当前运行已接受 Gateway 5c2645b1 / ELF e6873156（会话未读有界批读、群提交立即唤醒、既有在线维护批量），Message be8b5dde / ELF25487337，File原版本。后续大群、文件快照、收件确认合并都是保存了代码的实验候选，实验结束恢复原映像及完整配置；不能把不同候选的最优指标拼成一个已经验收的版本。

## 哪些功能实际覆盖

源码33类Gateway入口：28个公开请求已走真实协议链；私聊/群聊接收ACK和Pong实际发出核对；两类内部转发由跨Gateway业务间接覆盖，独立认证/故障入口尚未验收。功能包括登录/资料、好友请求创建/接受/拒绝/列表、私聊及幂等/历史/已读/未读/会话页、群创建/读取/更新/加入/离开/邀请/踢出/角色/禁言/转让/解散/成员分页/我的群/发送及重复与越权拒绝、文件Begin/重复/查询/跨所有者拒绝/取消，以及真实RPC流上传/续传/下载。

这些覆盖确有功能衔接和交叉：接受好友后发送私聊、读取后核对未读、禁言后拒绝发送、文件跨主体访问拒绝、群消息跨Gateway送达/最终SQL确认。但“操作链正确”不等于每个接口都完成高频压测。容量主场景仍集中在私聊、会话列表、两人群；好友/群管理/历史/文件控制/MCP没有各自独立并发曲线及高负载混合P99。

当前公开群上限500；内部5000收件快照防护不能当作5000人群能力。离线重连、多端同时会话、权限撤销与并发发送竞态、热点群、慢消费者、过载后恢复、TLS、MQ积压/重放、数据库/Redis故障、长期soak、并发大文件续传故障，尚未完成统一版本性能与正确性验收。

## 两个审查纠正：实际worker与客户端测量开销

历史文档把message_executor代码默认8worker当作实际运行并发。运行容器环境是TINYIMX_MESSAGE_WORKER_THREADS=16，每个Gateway16，control business4；已审阅的runtime/SQL/confirm对照同映像同完整环境保持，所以单变量对照仍成立，但4→8的解释错误，正确是4→16。通过只追加纠正保留历史数字与原失败。

更关键：群微测试在send后、pump读响应前，json.dumps(indent=2)并write_text重写整个累积all-requests文件；每个response又同步open/write/close timeline，接收ACK在此后发出。证据规模随着固定2→16→65→100顺序增加，客户端自身CPU、证据写入与等待会影响观察时刻及后续ACK。

新measurement-client-io-audit-20261006只在同Guest/原文件系统做离线重放，没有socket/SQL/重启/清理，事前审计新有界scratch。每case/size8次，4case共128次prefix重放；前一条已完整的130行约1.62MB，100人send后写证据平均47.310/56.151/56.155/61.132ms（不同case，观察最大80.258ms），编码CPU均值44.985–57.818ms；65人0.74MB约15.574–35.507ms。99条模拟接收timeline逐条open/write/close共32轮，平均11.319ms，范围6.589–20.456ms，body是合成形状，不能称为精确实际packet耗时。

已证明测量方法具有不可忽略的观察负担；没有测到TCP进入客户端内核的精确时刻，也没有证明这些时间全部相加或全为服务端慢。不能从历史ALL直接减47–61ms、不能把原FAIL改PASS、不能假定所有历史均被同量污染。相同客户端对照仍提供方向证据，但后续必须先将证据输出移出计时关键路径，并测生成器延迟/队列/CPU，保留旧合同及新旧并行观察后重新验收。

## 当前瓶颈及未解决的问题

1. 会话逐项Redis往返已解决，是确定且已接受的收益。服务器GET数没变，网络/租借成本下降；standalone Lua有界50，Redis Cluster跨slot能力未验收，SQL与Redis无跨存储原子快照。
2. 群业务一条消息会扩成多收件人的领取、路由、Get、投递、ACK及确认。completion和route批量减少已测瓶颈，Get和Confirm仍同步占用有限worker。更多并发引入下游SQL行锁、池与RPC调度竞争，瓶颈转移而非每次改动均总体收益。
3. 实际SQL诊断100人旧scalar确认每33条3267 UPDATE，4worker6.062ms/实际16worker11.160ms；Get SQL0.637/0.946ms与约20msGet RPC不相等。少量池0槽和1.127ms平均slot等待存在，不能解释所有延迟。fsync/行锁、同步调用和调度都需逐请求关联，不能把全部归给磁盘或盲目扩池。
4. 20k慢私聊同MID交集19条：send→ACK均165.118ms，仓库47.998（其中commit23.791），仓库前64.905、后52.214ms。是偏置慢样本，证明有多阶段成本，不能把嵌套阶段相加或当总体P99/唯一CPU根因。Redis Acquire诊断同样不支持盲目扩大池。
5. 测量客户端同步大证据写入刚量化，必须先消除观察瓶颈再判断100ms以下能达到哪里。低频日志有采样偏置，尚缺同请求跨Gateway/Message/SQL全链时间分解及生成器独立资源验证。
6. AI原profile地址host.docker.internal:11434、qwen3:8b与Guest127.0.0.1:11434、实际qwen2.5:7b不匹配；MCP原static principal=1未找到用户，不是多用户安全身份闭环。自有身份工具测试正确不等于生产配置已修复。AI常驻服务也未在19容器中运行，实际是一轮CLI；CPU模型占绝大多数完整Agent时间。
7. 项目主README仍为GitLab模板。大量工程证据已有专门文档，但缺面向外部的清晰功能表、架构、可复制部署/构建步骤、验收范围与代表性benchmark入口；当前封闭增量构建有输入SHA，不应假定已验证从干净checkout一条命令复现所有构建。对简历展示是明显问题。

因此细节尚未全部优化；除已确认性能问题，还有尚未覆盖的正确性/故障/高并发边界。未覆盖不是已证实产品bug，但不能按已完成给承诺。

## 竞争力与可诚实使用的表述

已有竞争力的部分是：可演示的IM功能、真实1万长连接指定混合回归、保持持久化/鉴权的有界批量优化、逐消息身份/SQL/wire核对、失败候选不冒充成果、代码/证据/回滚留档。100/s私聊和20/s整页的速率相对1万在线用户较轻，加上60秒窗口，尚不足以称为高活跃万人生产容量或行业领先。

适合简历的表述：在8vCPU/约16GB VMware开发环境、保留现有应用的条件下，验证1万认证TCP长连接，指定私聊100条/s+50项会话页20次/s+两人群2条/s混合负载，私聊ACK P99上界50.9–57.5ms、会话页P99 34.2–38.3ms；通过同ELF ABBA将指定10k场景会话P99保守降低80.46%，保留鉴权、精确未读语义及持久化确认，并对SQL/wire/身份逐条对账。群completion/route组件收益必须注明候选/有限规模，暂不能写5万全功能极致/百万QPS/高可用生产成熟。

下一阶段顺序：先改良证据采集并做双观察校验；再逐请求拆Get/Confirm/RPC队列与下游竞争，依据关键路径选有界改动；然后同版本10k/20k/30k/50k、不同消息/群规模/文件频率开环曲线，逐接口P50/P95/P99/最大/错误/积压/CPU/磁盘/生成器迟到，加入热点/多端/重连/权限竞态/故障与小时级稳态；最后整理可复现入口和README。业务SLO分别定义：发送ACK、实际送达、未读可见、文件首字节/吞吐、AI首token/完整答案。优良目标必须绑定负载、硬件和语义，才能判断还能优化多少。
