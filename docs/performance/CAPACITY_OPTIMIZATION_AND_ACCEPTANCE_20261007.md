# TinyIMX 万人至五万人容量优化与验收

当前可以开始使用已验证的项目成绩撰写简历，同时继续优化。容量目标需要绑定认证连接数、实际请求速率、群规模、持续时间和确认语义；“最优”不能作为没有负载定义的验收条件。

## 当前状态

| 场景 | 实测范围 | 状态 |
|---|---|---|
| 万人指定混合 | 10000 认证 TCP 连接；私聊 100 条/s、会话页 20 次/s，主要窗口 60 秒；补充两人群 2 条/s与功能交叉 | 两轮开启优化：私聊 ACK P99 上界 57.5/50.9 ms，会话页 P99 38.293/34.199 ms；该范围通过 |
| 两万人指定混合 | 20000 认证连接、私聊 135 条/s、会话页 20 次/s、交叉功能链 | 8100 私聊、1200 会话页与最终状态核对正确；私聊 ACK P99 上界 201 ms、会话页 P99 155.029 ms，延迟失败 |
| 大群串行诊断 | 100 连接；2、16、65、100 人群，每规模每轮 30 正式消息 | 正确性通过；65/100 人群尾延迟未通过；4–8 RPC 轮询线程没有稳定收益 |
| 五万全部业务 | 认证连接、持续业务、各功能交叉、文件和 AI 的联合目标 | 尚未验收；历史部分连接/登录试验不能当全部功能能力 |

现有数据是不同测试版本、不同业务合同的结果，不混用为同一版本的容量曲线。

## 下一轮先修两万人尾延迟

先保持已有 20000 连接、135 条/s私聊和20次/s会话页的原合同，给同一 MID 建立 Gateway 进入与工作队列、权限调用、Message RPC、仓储、提交、路由、未读更新和返回观察的关联。已有19条偏置慢样本的发送至ACK均值约165.12ms，仓储前约64.91ms、仓储约48.00ms、仓储后约52.21ms；提交约23.79ms嵌套在仓储内。这说明多段等待共存，不代表总体分位数，也不能将嵌套时间再相加。

客户端发送迟到、读取、解码和证据写入须分别记录。新观察方法保留原计时合同与全部失败，先验证记录数、MID身份、缓冲上限、关闭落盘和重复/遗漏；不得直接从旧延迟中减去一段观察时间后宣布通过。

心跳已有即刻 Pong 和独立有界在线状态维护。它不能重复当作新优化，也不能把某时间点 UserService CPU 较高直接归因到心跳；需要对应登录爬坡和稳态阶段。

## 依据关键路径选择代码改动

| 候选 | 当前依据 | 必须保留与验证 |
|---|---|---|
| 有序分条调度公平性 | DrainStripe 持续排空当前分条；慢同步任务可能占用共享 worker | 同键 FIFO、任务只执行一次、无丢唤醒、过载拒绝、取消语义、优雅停机；先确定热点与冷门分条的实际等待 |
| 群持久数据的有界批量读取 | 每收件人 Get 与 ACK 读取存在多次 RPC/SQL 往返；选定调用约10ms在 handler 范围外 | 原权限、MID/UID、租约、状态与重启恢复；保持 peer/ACK 相同 identity 排序，不以缓存跳过验证 |
| 私聊提交与后续同步调用 | 两万人慢样本同时有提交、RPC残差、路由及未读等待 | ACK与持久化合同、Outbox、重复请求和错误传播；按同 MID 关键路径判断，避免扩大线程或连接池转移竞争 |

以上均为待验证候选，不是已证实的唯一根因。4–8 Message RPC 轮询配置的性能候选已经否定；原运行镜像与配置保持。

## 容量扩大顺序

1. 先重现并修复已有20k/135条私聊每秒的失败点；同版本对照须同时通过原正确性、错误、积压和P99门槛，再提高速率。
2. 通过后，在同一版本下测试10k、20k、30k、50k，区分登录爬坡、在线保持与实际活跃业务；保持请求比例和群规模分布，记录实际已提供和已完成的负载。
3. 以现有10000连接配100条私聊每秒为活跃度基准，可规划20k/200、30k/300、50k/500条每秒，列表相应20/40/60/100次每秒；这些是未来计划，不是当前已实现指标。群投递同时报告群发送数与实际收件数，小群、大群和热点单独计量。
4. 每个容量点增加足够预热和至少10分钟稳态，最终候选增加小时级稳态以及重连、离线、多端、权限竞争与受控故障。原60秒成绩保留，不能改名为小时级稳定性。

每次只改变一个候选，在同硬件、服务配置、密码校验、持久化、超时和观测方法下比较。写明P50/P95/P99/最大、错误率、生成器迟到、连接丢失、队列积压、CPU等待、内存、磁盘与数据库锁等待。业务错误、持久化不确定或记录丢失不能被更好看的平均值抵消。

## 功能验收分别定义

| 功能 | 主要性能指标与正确性条件 |
|---|---|
| 登录与重连 | 登录速率、成功延迟、失效旧会话、异常输入与认证成本 |
| 私聊与群聊 | 发送持久化ACK、首个及全部实际收件、确认与离线恢复；热点/群规模/跨Gateway |
| 会话和历史 | 完整授权页的P99、未读可见延迟、精确计数、分页及读写并发 |
| 社交和群管理 | 读写P99、权限拒绝、退群/踢人/禁言与投递竞争 |
| 文件 | 创建与授权P99、首字节、吞吐、并发续传及跨所有者拒绝；不能用创建接口速度代表完整传输 |
| AI与MCP | 模型就绪、首token、完整回答、工具授权和并发排队；CPU模型当前秒级，单独验收 |

现有100ms门槛先按原合同验收；更低延迟目标绑定具体业务再制定。文件吞吐与AI完整回答不套用消息ACK的同一时间值。“全部功能”由逐项覆盖表和相互交叉场景证明。

## 简历与版本记录

简历使用已接受的万人指定混合结果、未读批量优化与消息正确性设计。20k尾延迟、大群和50k容量作为持续迭代目标；每轮修改前保留审计与前镜像，记录代码、镜像、原始请求、失败原因、分析、回滚和Git提交。对外展示补齐项目README与可复现构建部署入口，并分别验证干净checkout和实际部署，避免把现有封存增量构建写成一键可复现。

本轮只整理事实、项目描述与下一阶段验收，不改产品代码、运行配置、业务数据或主机设置，不启动新的高负载试验。所有旧结果与失败记录保留。
