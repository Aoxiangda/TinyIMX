# SDK 文本构造组件成本（PERF-217）

2026-10-21。状态：32 个独立进程测量点完成，候选 SDK 的协议对象、protobuf 及延迟参数 helper 均保持固定。没有服务负载、网络消息或产品配置修改，没有新的完整 A/B 性能成绩。

## 来源及实际执行

旧 R183 直接链接原 SDK 失败，原因是其 protobuf 符号未动态导出；该失败保留。本轮直接使用已完整重建候选的 `build/proto/libproto.a` 和同一 `deps/grpc-v1.46.3/lib/libprotobuf.a`，两者均已核对为候选真实链接输入。未调用原库私有地址，测量程序也没有加载 `librocketmq` 或共享 `libprotobuf`。不能将结果改称原安装 SDK 的实际回调计时。

协议对象为固定 API `bc8e1845a8b0a1b5ec828690324401a323244354` 的 `ReceiveMessageResponse`；protobuf 3.19.4、fmt 9.0.0、C++11/O3。使用实际 `LazyLogValue` 和 spdlog 的 DEBUG 宏，INFO 级别关闭 DEBUG、backtrace 未启用。每个进程先验证 DEBUG 开启时两个开关均求值一次，预热后测量 100,000 次，采集进程 CPU 时间及墙钟，核对调用数、文本长度校验和及协议对象不变。

正文来自 E 盘已实际恢复且 Broker 曾逐字节核验的 R165C 42,000 条事件快照。全部事件正文长度均为 364 字节。`actual-p50`、`actual-p99` 是按**正文长度**排序取出的两个记录位置，记录哈希不同、长度相同；名称不代表延迟分位。另有纯 ASCII 的 128/8192 字节尺寸控制。

每个正文分别测量仅 body 的协议对象，以及加入合成常见字段的协议对象。后者包括 topic、tag、key、消息 ID、时间戳、队列、96 字符回执等；这些字段不是从真实 SDK 接收响应捕获的，不能作为实际响应的完整重放。

## 实测 CPU 成本

每个格子为 OFF/ON/ON/OFF 的两个 OFF 点的单次 CPU 微秒；ON 在全部测量点的正文生产者调用数均为 0。

|正文|正文长度|仅 body，OFF 两次|加合成字段，OFF 两次|
|---|---:|---:|---:|
|实际记录 p50 位置|364 B|0.772 / 0.777 μs|2.657 / 2.695 μs|
|实际记录 p99 位置|364 B|0.791 / 0.763 μs|2.665 / 2.663 μs|
|ASCII 尺寸控制|128 B|0.408 / 0.403 μs|2.136 / 2.098 μs|
|ASCII 尺寸控制|8192 B|4.056 / 4.033 μs|5.927 / 5.890 μs|

完整原值及 ON 循环成本在 `benchmark/results/peer-20261017/PERF217-sdk-proto-component-cost-r1/`。ON 微小循环成本受该独立程序的优化、常量状态与调用点影响，不用它宣称真实 SDK 每条消息的总开销或整机下降百分比。这里只知道该组件可避免一次文本构造，不知道实际业务中各类表达式的调用频次、完整协议形状、缓存影响及 RPC 成本。

32 个点均通过生产者次数、DEBUG 控制和不可变对象检查。原/新 SDK、协议静态对象、2,292 个容器、原业务及九个保护库、binlog 后置核验通过。固定的静态 protobuf 依赖未改，SDK 日志候选仍默认关闭。

## 对下一步的影响

不将这项微秒级组件成本当作整机忙核差距的解释，暂不推广 SDK 日志候选。优先完成已冻结限页候选的完整控制，再独立测 SDK 同库 OFF/ON 和原库回归。

已经记录的较大结构差异是应用批量 ACK 仍提交 N 次 RPC。官方协议支持多 entry，但现有 C++ SDK 的聚合回调不能携带逐条结果；该扩展先完成结果映射安全基础，见 [PERF-218](MQ_WIRE_ACK_BATCH_20261021_R218.md)。完整发压的内存门槛没有降低。
