# TinyIMX 无外键改造与验收记录（PERF-146）

本轮按用户确定的工程规范实施：业务表和 native 引用登记表均不使用数据库外键或级联；引用校验和生命周期由应用代码维护。保留主键、CID/操作 ID 等唯一键、索引、MySQL 事务和本地原子提交。它们分别服务于身份、幂等和提交一致性。

## 应用代码的约束

- 新增 `common/db/LogicalReferences.h`：枚举限定表名，使用无符号 ID，去重并按 256 项分批检查。整批检查完成后才允许首条写入，不自动提交、不隐式重试、不改变调用方的事务。
- 私聊覆盖普通保存、调用方事务保存、BEGIN/INSERT 路径及两种批量路径；群消息及投递校验群、消息归属与全部接收者。
- 群仓储覆盖建群、加入/重新加入、历史、操作去重、转让、解散和结束历史的操作者引用。原好友申请/接受已在事务中按升序锁定并检查双方用户，本轮保留该实现。
- 文件仓储校验所有者、上传会话和块引用；额外检查文件所有者及上传会话对应文件，拒绝仅 ID 存在但归属不匹配的组合。
- native 启动改为要求显式的无外键结构。冷用户引用登记检查 owner 与用户后再落盘；暖用户缓存、SQL 所有权租约、指纹、CID 规则和原子消息/事件提交保持既有职责。

应用生命周期为**父记录保留、ID 不可变**。现有服务没有用户/群/文件父记录的物理删除或 ID 重编号 API；禁用用户、解散群和取消上传使用状态变更。取消/退出仍由原业务状态与历史权限校验控制，保留父记录不表示继续授权。这样无需在每条私聊上新加父行锁，也不会发生应用物理删除与子记录新增的竞态。

该契约不声称能够限制拥有任意 SQL 权限的管理员。运行账号应收敛权限；物理清退、重编号或迁移需要独立的停写、引用审计及数据保留流程。不能恢复旧的 DELETE CASCADE，也不能把裸 SQL 注入脏数据后的状态描述为应用已保证一致。

## 结构与迁移

总建表、分域建表和 native 建表去掉外键，并显式保留原本可能由 InnoDB 隐式补出的引用查询索引。现存安装使用 `db/migrations/016_remove_business_foreign_keys.sql`，仅操作列明的 13 张业务/引用子表；旧 RTT 测试表不在范围内。

迁移要求明确选择 schema，并设置 `@tinyimx_confirm_quiesced=1`。先审计每条逻辑引用，有孤儿数据即拒绝；之后逐项删约束，保留记录、主键、唯一键及全部索引，可中断后重入。未使用 `foreign_key_checks=0`。DDL 自提交，所以不能把整个迁移称为可事务回滚的操作。

还修正了历史分域迁移中硬编码 `USE tinyimx` 的问题：迁移遵从调用方指定的数据库。首次隔离夹具准备因此只建到 22 条约束；文件表的 `CREATE IF NOT EXISTS` 命中了已存在的原库表，未改其记录或结构。失败保留；修正后补齐隔离库文件表，实际 28 条约束的迁移验收通过。

部署脚本已接入 016 与零外键验收。现有旧二进制及保护数据库本轮没有原地替换：旧 native 二进制仍要求两条 FK，不能先删正在使用的约束再继续运行旧写入逻辑。正式替换需要完整新服务构建、业务端到端验收、停写和明确迁移顺序。

## 与性能主线的连接

R145 的 42,000 条消息、MQ 完整事件、20,000 个 Redis 计数与无 Retry/DLQ 正常链已全部闭合，但 CPU 采样器在开始记录前解析进程表失败。该轮没有有效应用调用栈，保留失败，不作归因。

R147 使用全新 schema/topic，先验证实际 stdout/stdin 软件 CPU 采样管道，再运行固定 R30 的诊断基线。采样不修改持久化、权限或 ACK 边界；采样轮不能充当正式性能收益。取得调用栈后再选择一项明确工作量做消融，随后与无外键候选一起进行完整同负载验收。

后续已推进至R148：1237个有效样本、零丢失，完整42k/MQ/Redis正常链通过。根据事件扫描热点实现R149单开关候选，局部OFF/ON/ON/OFF、8组契约/sanitizer及4次真实终止恢复通过。R150全部9服务及源码已封存，R151将执行相同二进制的完整负载对照。详细取舍和性能适用范围见 [扫描消融记录](CPU_SCAN_ABLATION_20261020_R149.md)。

## 2026-10-21 后续验收

R157 已以全部九个新产品完成四轮、共 168000 条消息的正式完整负载验收：私聊、确认、全部本地索引、MQ 全量事件和 Redis 投影均一致；每轮结构均为零外键、零孤儿引用，原业务库与九个指定测试库保留。R165 的当前版本组件诊断及 R169 OFF1 的新代码基线各完成 42000 条正常链验收，仍为零外键。各轮均正常停机、无 OOM，恢复原服务；这些是隔离环境验收，原业务库尚未原地切换。

R157 的键索引候选只减少约 1.97% 整机忙核，ACK P99 上升约 2.69%，默认仍关闭。R165 的新调用栈进一步定位到发布线程反复解析正文；R169 OFF1 实测发布 42000 个事件却解码 1271773 次。R172 完成前置 held 筛选 ON 的全量对照：解码仅降到 1200998 次、CPU 约减少 1.26%、ACK P99 反而上升约 2.15%，故没有推广，也没有把该第一对照称为完整 ABBA。

进一步的真实转发线程实验确认队列仅空出一个位置时，固定页会解析大量未准入的尾部数据。R173 按空位限页候选通过旧契约、sanitizer、真实顺序/停机/恢复和四次终止恢复验证；R175 冻结程序后，正式 OFF1 因发压前内存未达 8 GiB 在零流量阶段拒绝，未形成性能成绩。R180 继续落实原生未读快照的有界批量 RPC 和整批兼容回退截止时间；九程序、真实网络、sanitizer、实际持久 owner 和既有原生合同通过。详见 [批量 RPC 改动及证据](NATIVE_UNREAD_BATCH_RPC_20261021_R180.md)。这些新候选默认仍关闭，不将契约通过包装为整机收益。
