## 采样结果及真实失败

R402-r1 错误地要求空闲 Relay 至少有 100 个样本，解码在此中断。r2 保留原输出，单列 Relay 的零样本，继续完成三份 C++ 与两份 JVM 记录的离线解码：Gateway A 378 个、投影器 173 个、Relay 0 个。两份 C++ 有样本的记录均为零 lost；内核地址受既有权限限制，未改系统设置，也没有把未知地址命名为某个内核函数。

投影器样本仍出现 Protobuf TextFormat；历史同一 SDK 的实际调用栈及反汇编已证实 `OnReadDone → DebugString` 在 DEBUG 级别检查前求值。现有组件微测只说明微秒级格式化成本，尚不能解释整机数核差距。Broker 的 146 个 Java ExecutionSample 中有 31 个落在 TimerWheel.flush；这是后续审计入口，不能直接推算其占用整机 CPU 的比例。NativeMethodSample 中大量 epollWait 也不能视作等比例忙 CPU。

Message 采样失败：留下 96704 B perf 文件但无 CPU 样本；原采集器未保存 perf 返回码及临时容器退出状态，无法据此确定 OOM、文件描述符不足或线程附加竞态。R398 原始头部与 stderr 已保留。下一次改用限定 Message cgroup、固定环形缓冲的采集方式，覆盖后续新线程，并在移除临时容器前保存退出码、OOM 状态、时间及丢样本信息；不放宽宿主安全设置。
